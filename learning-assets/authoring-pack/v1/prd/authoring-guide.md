# PRD 编制指南

## 编制顺序

1. 读取用户需求、已确认澄清记录和允许读取的仓库事实。
2. 先使用 `template.md` 建立完整正文，不跳过任何章节。
3. 只写已确认的业务事实和用户可观察行为；事实不足时提出少量会改变范围、角色、主流程或验收口径的澄清问题。
4. 对照 `self-check.md` 自检并自行修订一次，再提交给用户验收。

## 产品与技术的边界

PRD 要回答“为什么做、为谁做、用户如何使用、什么结果算完成”。API、数据表、队列、事务、缓存、重试、文件目录、前后端组件和具体测试框架属于 TD，不应写成 PRD 的硬性要求。

可以描述用户可见的约束，例如“提交后可查看进度”“失败行可下载查看”“不改变既有查询结果口径”；不要猜测这些能力如何实现。

## 写作质量

- 用简洁中文面向产品、研发和验收人员写作；不要输出内部 `REQ-*`、`DEC-*`、`AUTH-*` 等审计标识。
- 正文“文档信息”不得声明“待审批”“已审批”等生命周期状态；该状态、审批人和审批时间只以 Runtime 快照为准。
- 将已知事实、用户明确选择和暂未决定事项区分清楚。未决定且影响产品范围时，必须澄清。
- “兼容既有能力”必须说清保持不变的对象和用户可见口径，不能只写“兼容”。
- 验收标准必须可由人或测试验证，避免“体验良好”“合理处理”等不可判定表述。
